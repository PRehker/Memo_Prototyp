# AGENTS.md — Team Rules for AI Coding Agents

Every coding agent (Vibe, Claude Code, Codex, Cursor, ...) reads this file
automatically at the start of every chat in this repository. Follow these
rules in every prompt, on every branch, in every commit. No exceptions.
Also read `CONTEXT.md` at the start of every session — it holds the project
big picture and the user-story list.

## 1. Always-on agent setup: RTK + Caveman + Ponytail

At the start of every session, before doing any other work:

1. Load the **`caveman`** skill and keep it active for the whole chat
   (compresses internal reasoning only — answers to humans stay normal,
   clear, professional).
2. Load the **`ponytail`** skill and keep it active for the whole chat
   (smallest complete change on every coding task).
   Both skills ship inside this repo under `.agents/skills/`, so they are
   available in every checkout — no personal installation needed. If your
   agent cannot find them there, say so instead of skipping them.
   If a **`groundcheck`** skill is present in `.agents/skills/groundcheck/`,
   load it and keep it active for the whole chat as well.
3. Use **RTK** for every shell command: run `rtk <command>`
   (e.g. `rtk git status`, `rtk npm test`, `rtk pytest`) so command output is
   compressed before it enters the chat. Check with `command -v rtk`; if it
   is missing, install it once with `brew install rtk` (https://www.rtk-ai.app)
   and mention that in your reply.

If you are an agent reading this, confirm in one line that caveman and
ponytail (and groundcheck, if present) are loaded and that you will route
shell commands through `rtk`.

## 2. Verify everything against real data

Nobody on this team guesses. Every piece of code and every assumption must be
checked against real data before it is used:

- Before writing code that touches a library, API, SDK, config key or piece of
  hardware (e.g. the PN532 NFC chip, speech-to-text, text-to-speech), verify it
  against **official developer documentation** and **official demo/example
  projects**. Fetch the docs with the web tools if they are not already in the
  repo.
- Check the exact version pinned in this repo (`package.json` + lockfile,
  `requirements.txt` + lockfile, Podfile.lock, ...) and verify the API against
  **that version's** docs — not against "the latest" docs.
- Grep this repo for existing usage of the same API and follow the existing
  pattern before writing new code.
- State every assumption explicitly ("I assume X") and verify each one against
  real data — documentation, a demo project, the installed package source
  (`site-packages` / `node_modules`), or by running the code. If an assumption
  cannot be verified, say so out loud; never proceed on it silently.
- Prove it works: run the code, the tests or the build and read the output.
  Never claim something works, is deprecated or is correct without having
  executed or read real evidence for it.
- If documentation and actual behavior disagree, trust the executed code and
  the installed source, and note the discrepancy in your reply.

## 3. Git rules — user-story branch management

- **Never commit directly to `main`.** All work happens on a story branch.
  Exception: the admin branch **`operative`** is reserved for organisational
  repo changes (docs, rules, scripts, config) committed directly by the admin.
  Code features still go through story branches.
- Every task is kicked off with a **user story** from the team's Trello board,
  pasted into the prompt with its full text, written like:
  `US-12: As a <role> I want <goal> so that <benefit>`
- When a prompt contains a user story:
  1. Extract the story ID (e.g. `US-12`) and a short slug from the story
     (e.g. `login-form`).
  2. Run `./scripts/story-branch.sh US-12 login-form`. The script fetches
     origin, then:
     - if a branch for that story already exists (locally or on origin,
       `story/us-12-*`), it checks it out;
     - if not, it creates `story/us-12-login-form` from the latest
       `origin/main` and switches to it.
  3. Do all work and all commits on that story branch.
- Commit messages start with the story ID: `US-12: short description`.
- Always commit and push with the **user's own git credentials** (the
  `user.name` / `user.email` from their git config) — never override them
  with an agent/AI identity via `-c user.name=...`. Commit messages never
  contain AI/agent signatures, "generated by" notes or co-author trailers:
  the human doing the agentic development gets the credit.
- Push the story branch so the team can see it: `git push -u origin <branch>`.
  When the story is done, open a pull request into `main` and **leave it open —
  only Philip approves and merges PRs**. Never merge your own PR, never mark
  a story done anywhere else; the merged PR is the only signal.
- Never push to `main`, never force-push, never delete other people's branches.
- Keep the story branch current: before finishing a story, run
  `git fetch origin && git merge origin/main` inside the story branch and
  resolve any conflicts there.
- If a prompt contains no user story and the current branch is `main`, ask
  which user story the task belongs to before writing any code.

## 4. Stay in sync — timestamp every prompt, pull after 2h of inactivity

- At the start of **every turn** — every prompt the user sends, in every
  session, even after a short break — run `./scripts/sync-check.sh` as the
  very first action, before any other work.
- The script always writes the current time to `lastWorkedTimestamp.txt`
  (repo root, gitignored).
- If the previous prompt was more than **2 hours** ago (a new session after
  a break, or the same session after inactivity), the script syncs with
  origin first: `git fetch origin`, then `git pull --ff-only` on `main`, or
  `git merge origin/main` on a story branch. Work must not start on stale
  state — this surfaces merge issues early instead of at PR time.
- If the sync reports conflicts or fails, resolve them (or report them to
  the user) before continuing with the actual task.
- Some agents can automate this with a project hook (e.g. Vibe's
  `.vibe/hooks.toml` running `./scripts/sync-check.sh` on `pre_agent`);
  otherwise just run the script yourself at the start of every turn.
